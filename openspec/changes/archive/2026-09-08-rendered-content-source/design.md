## Goals / Non-Goals

**Goals:**

- Que el `.md` de una entrada construida con Elementor o con una plantilla de contenido fijo contenga el texto que ve un visitante, decidido por condicionales de WordPress y no por adivinar.
- Que el loopback sea seguro (solo el propio host, sin recursión, acotado en tiempo y tamaño) y que su fallo degrade al comportamiento actual sin descartar ítems ni ocultar el problema.
- Que un administrador pueda forzar el origen por tipo o por entrada y afinar la región con un selector, y que Diagnóstico le diga si el loopback funciona.
- Encajar en los patrones existentes (builder, Runner/State, Settings/pestañas, meta box, probe/Report) para implementar en un commit por grupo.

**Non-Goals:**

- Renderizar el constructor "desde dentro" (invocar la API de Elementor, Divi, etc.): cada constructor tiene su API y su estado de front-end; el loopback los cubre todos.
- Un motor CSS completo o un selector por tipo de contenido: un selector global y una lista automática cubren los temas habituales; lo demás va por filtro.
- Detectar cambios en plantillas o widgets globales para regenerar antes de tiempo: cada ciclo ya regenera todos los ítems.
- Cabecera "Cache-Control" distinta para documentos de respaldo, o cualquier cambio en la negociación de contenido.
- Sondear el loopback en cada guardado de ajustes.

## Decisions

### A1. `ContentSource::resolve( WP_Post ): array{source, reason}` con condicionales en orden fijo

Nueva clase `WPASL\Markdown\ContentSource` (recibe `Settings`). `resolve()` devuelve `array( 'source' => 'editor'|'rendered', 'reason' => string )` y pasa por `apply_filters( 'wpasl_content_source', $result, $post )`. Orden y función de WordPress que sustenta cada condicional:

| Orden | Condición | Fuente | Razón |
| --- | --- | --- | --- |
| 1 | `get_post_meta( $id, '_wpasl_content_source', true )` ∈ {`editor`, `rendered`} | meta protegida (A3) | `post_override` |
| 2 | `Settings::get( 'content_source' )[ $post_type ]` ∈ {`editor`, `rendered`} | ajuste (A4) | `post_type_setting` |
| 3a | `'' !== get_page_template_slug( $post )` | `_wp_page_template` (post types con `page-attributes` o `templates` en `theme.json`) | `page_template` |
| 3b | meta de constructor presente con su predicado | `get_post_meta()` | `builder:<id>` |
| 3c | archivo de plantilla específico sin impresión del editor | `locate_template()` sobre la jerarquía de `get_single_template()`/`get_page_template()`; `resolve_block_template()` en temas de bloques | `template_file:<archivo>` |
| 3d | contenido del editor convertido vacío o < umbral | `DocumentBuilder::render_html()` + conversor | `empty_editor` |
| 4 | nada aplica | | `default` |

- **3b, lista de constructores** (`ContentSource::BUILDER_META`, filtrable por `wpasl_builder_meta_keys`, forma `id => [ meta_key, valor esperado o null = "no vacío", meta adicional obligatoria o null ]`): Elementor `_elementor_edit_mode` = `builder` y `_elementor_data` no vacía; Divi `_et_pb_use_builder` = `on`; Beaver Builder `_fl_builder_enabled` no vacío; Bricks `_bricks_editor_mode` = `bricks` o `_bricks_page_content_2` no vacío; Oxygen `ct_builder_shortcodes` o `ct_builder_json` no vacío; Breakdance `breakdance_data` no vacío. Las claves se fijan a partir de la documentación y el código de cada constructor durante la implementación (tarea explícita, como se hizo con los plugins SEO); una clave errónea solo hace que el constructor no se detecte y el caso lo recoja 3c o 3d. WPBakery queda fuera a propósito: guarda shortcodes en `post_content` y `the_content` los renderiza.
- **3c, lectura del archivo.** Candidatos (`wpasl_template_candidates`): para `page`, `[slug asignado, page-{slug}.php, page-{id}.php]`; para el resto, `[slug asignado, single-{tipo}-{slug}.php, single-{tipo}.php]`; nunca `single.php`/`page.php` genéricos (imprimen el editor en cualquier tema sano y no dicen nada del tipo). La ruta la da `locate_template( $candidates, false, false )` y pasa por `wpasl_template_file` (los tests apuntan a un archivo temporal). Se lee con `file_get_contents()` limitado a 256 KB; una plantilla "imprime el editor" cuando contiene la subcadena `the_content` (cubre `the_content(`, `get_the_content(` y `apply_filters( 'the_content'`) o `wp:post-content`; es **inconcluyente** (no cuenta a favor de `rendered`) cuando contiene `get_template_part(`, `locate_template(`, `include`/`require` con argumento no literal, o `get_template_part` con argumentos literales cuyo archivo resuelto también sea inconcluyente (se sigue un nivel, máximo 10 partes). Así `single-solucion.php` con HTML fijo → `rendered`; el `single-solucion.php` de un tema que delega en `template-parts/content` con `get_post_type()` dinámico → no cuenta y decide 3d. Caché en memoria estática por proceso, clave `ruta:filemtime`, para no releer el mismo archivo por cada ítem del lote. En temas de bloques (`wp_is_block_theme()`), se usa `resolve_block_template( 'single'|'page', $candidatos_sin_php, '' )` y se inspecciona `->content` buscando `wp:post-content` (las partes `wp:template-part` cuentan como inconcluyentes). Verificado: `resolve_block_template()` existe desde 5.8 y el mínimo del plugin es WordPress 7.0.
- **3d, umbral.** `wpasl_editor_min_chars`, por defecto 100 caracteres del cuerpo Markdown convertido (recortado, sin el H1). Se evalúa el último porque cuesta una conversión; `DocumentBuilder` reutiliza ese cuerpo cuando el resultado final es `editor` para no convertir dos veces.

Alternativa descartada: heurística de longitud comparando el texto del editor con el de la página renderizada. Obligaría al loopback en cada ítem (coste y tiempo) y decidiría por magnitud, no por causa; el usuario la descartó como criterio principal y aquí solo sobrevive como red final sobre el editor.

### A2. `DocumentBuilder` orquesta: resolver, obtener, extraer, convertir

- Constructor: `__construct( ConverterInterface $converter, ?ContentSource $source = null, ?RenderedPage $fetcher = null, ?ContentExtractor $extractor = null )`. Con `null` (tests que instancian a mano, servicios sustituidos) se comporta como hoy: origen `editor`. `Plugin::boot()` inyecta las tres instancias.
- `generate()`: `$resolution = $source->resolve( $post )`; si `rendered`, `$fetch = $fetcher->fetch( $post )`; si `ok`, `$html = $extractor->extract( $fetch['body'], $post )` (puede fallar con `no_content`); si cualquiera falla, `$html = render_html( $post )` (editor), `source = editor`, `fallback = true`, `error = motivo`. El HTML pasa por `wpasl_markdown_html` como hoy; el front matter añade `'source' => $source` justo después de `lang` (antes de `description`), y el resto del documento no cambia. Al final `do_action( 'wpasl_content_source_resolved', $post, array( 'source', 'reason', 'fallback', 'error', 'deferred' ) )`.
- Por qué la clave `source` va en el front matter: es la única señal barata para que un agente, el diagnóstico o un administrador (abriendo el archivo) sepan de dónde salió el cuerpo, y permite verificar en vivo el efecto del cambio. Coste: una línea; el orden de claves existentes no cambia.
- Diferido por presupuesto (B3): cuando `RenderedPage` informe `deferred`, `generate()` devuelve `null` **y** la acción lleva `deferred => true`; el Runner lo distingue de un fallo (B4).

### B1. Loopback en `RenderedPage::fetch( WP_Post ): array{ok, body, error, status}`

Nueva clase `WPASL\Markdown\RenderedPage`. Argumentos por defecto (filtrables por `wpasl_render_request_args( $args, $post )`):

```php
array(
  'timeout'             => 10,
  'redirection'         => 0,
  'limit_response_size' => 2 * MB_IN_BYTES,
  'reject_unsafe_urls'  => true,
  'user-agent'          => 'WP-Agent-Support-Layer-Render/' . WPASL_VERSION,
  'headers'             => array( 'Accept' => 'text/html', 'X-WPASL-Render' => '1' ),
  'sslverify'           => apply_filters( 'https_local_ssl_verify', false, $url ),
)
```

- URL: `add_query_arg( 'wpasl_render', '1', get_permalink( $post ) )`. Antes de pedir, se rechaza cualquier host distinto del de `home_url()` (mismo criterio que `CrawlerProbe::fetch()`), con `reject_unsafe_urls` como segunda barrera (`wp_http_validate_url()` acepta el propio host aunque resuelva a una IP privada).
- **Parámetro y cabecera, ambos.** El parámetro es imprescindible: sortea Cache Enabler (y cualquier caché que respete cadenas de consulta) y sobrevive a proxies que no reenvían cabeceras personalizadas. La cabecera es la marca que `Delivery` reconoce aunque un CDN reescriba la URL, y la que el administrador puede reproducir con `curl`. `wpasl_render` **no** se registra como query var (por eso no es `wpasl=render`): un parámetro registrado rompería la portada estática (ver Context), uno no registrado es invisible para `WP_Query`. `Delivery::is_render_request()` mira `$_SERVER['HTTP_X_WPASL_RENDER']` o `$_GET['wpasl_render']` (saneados) y `maybe_serve()`, `maybe_serve_404()` y `handle_md_suffix()` devuelven sin servir cuando es verdadero: **una petición de renderizado nunca recibe Markdown ni genera nada**, lo que elimina la recursión (petición `.md` → `generate_item()` → loopback HTML → `Delivery` no genera). `send_html_headers()` y `print_alternate_link()` no cambian: la respuesta es el HTML normal.
- Redirecciones: `redirection => 0`; si la respuesta es 301/302/307/308 con `Location` del mismo host, se vuelve a pedir (máximo 2 saltos); otro host o más saltos → `redirect_external_host` / `redirect_loop`. Un sitio con `home_url` en `http` que redirige a `https` falla con `redirect_external_host` solo si cambia el host; el esquema puede cambiar (mismo host).
- Motivos de fallo: `external_host`, `request_error:<código WP_Error>`, `http_<código>`, `redirect_external_host`, `redirect_loop`, `not_html` (Content-Type sin `text/html`, incluido `text/markdown`), `empty_body`, `deferred` (B3), y `no_content` lo añade el extractor. Un fallo devuelve `ok => false` con el motivo; nunca lanza.

Alternativa descartada: renderizar internamente cargando la plantilla del tema con `locate_template()` + `include` en un buffer. Requiere un `WP_Query` singular completo, los hooks de `template_redirect`/`wp_head`/`wp_footer` y los constructores registran su render en el front-end real; es frágil y, en cron, no reproduce la petición.

### B2. Generación bajo demanda: el loopback se hace en la petición

Cuando `Delivery::document()` no encuentra el archivo y `Runner::generate_item()` genera, el loopback se ejecuta ahí mismo con el tiempo máximo configurado (10 s). Justificación: la alternativa (servir el editor y encolar) devolvería un documento casi vacío con `Cache-Control: public, max-age=<intervalo>`, que un CDN o el propio agente guardarían durante un día; una espera acotada en la primera petición es preferible, y las siguientes sirven el archivo. Riesgo de un único worker PHP (el loopback espera a sí mismo hasta el timeout): el fallo se registra, el documento sale con el editor y Diagnóstico lo explica (D2). Si el loopback falla bajo demanda, el documento de respaldo se almacena igualmente (evita repetir un loopback de 10 s en cada petición) y el ítem se antepone en la siguiente ejecución (B4).

### B3. Presupuesto de la ejecución: deadline compartida por acción y diferido

`Runner::run()` dispara `do_action( 'wpasl_run_started', $deadline )` (`$started + $budget`) al empezar y `wpasl_run_finished` al terminar; `RenderedPage` escucha y, con deadline activa, acota `timeout` a `max( 0, deadline - now )` y devuelve `deferred` sin pedir cuando quedan menos de `MIN_TIMEOUT = 2` s. En `run()`, un `generate()` con `deferred` hace `array_unshift( $state['queue'], $post_id )`, no cuenta como procesado ni como fallo y rompe el bucle. Sin deadline (bajo demanda, `run_cycle()` con `PHP_INT_MAX`), timeout completo. Por qué una acción y no pasar el Runner al builder: `ItemGeneratorInterface` no cambia y `RenderedPage` sigue siendo instanciable sola en los tests. Nota: `wp wpasl generate` sin `--batch` usa `run_cycle()` con presupuesto infinito y por tanto timeouts completos; con `--batch` se aplica el de 20 s.

### B4. Fallos de renderizado en `State`, aparte de `failed`

- `State::defaults()` gana `render_failed` (`post_id => contador`) y `last_render_error` (`array( 'post_id', 'reason', 'time' )`). `Runner::register()` escucha `wpasl_content_source_resolved`: con `fallback`, incrementa `render_failed[id]`, fija `last_render_error`, emite `do_action( 'wpasl_render_failed', $post, $reason, $attempts )` y escribe en el error log (`[wp-agent-support-layer] Could not fetch the rendered page of %s #%d (%s), attempt %d; the editor content was used.`); con `rendered` sin fallback, `unset( render_failed[id] )`. Dentro de una ejecución se acumula en memoria (`run_render_marks`, como `run_marks`) y se vuelca al guardar; fuera, se escribe con un `State::record_render_failure()`/`clear_render_failure()` que carga, modifica y guarda (misma fusión que `mark_generated()`; `State::save()` pasa a fusionar también `render_failed` y `last_render_error` por fecha para que un fallo bajo demanda durante una ejecución no se pierda).
- El documento de respaldo **sí** se almacena y marca (`generated[id]`): el ítem no figura como pendiente ni como fallo de conversión (`failed` no cambia). `status()` añade `render_failed` (recuento) y `last_render_error`.
- `run()`: tras los ids nunca generados, antepone los ids de `render_failed` con contador `< max_failures()` (mismo umbral `wpasl_max_failures`) que estén en la cola; los que alcanzan el umbral quedan en su orden normal (cada ciclo los reintenta igualmente). Al completar el ciclo, `render_failed` se interseca con los elegibles como `failed`.
- `Scheduler::on_settings_updated()` compara además `content_source` y `content_selector` y llama a `clear_queue()` si cambian (sin tocar `generated`).

### C1. `ContentExtractor`: DOM, lista de selectores, limpieza y H1

Nueva clase `WPASL\Markdown\ContentExtractor` (recibe `Settings`). `extract( string $html, WP_Post $post ): array{ok, html, selector, error}`:

1. `DOMDocument::loadHTML( '<?xml encoding="UTF-8">' . $html, LIBXML_NOWARNING | LIBXML_NOERROR )` con `libxml_use_internal_errors( true )` (patrón de `LeagueConverter::clean()`); documento completo, sin `NOIMPLIED`.
2. Región: si `Settings::get( 'content_selector' )` (filtrado por `wpasl_content_selector( $selector, $post )`) no está vacío, se traduce a XPath y se prueba; si no coincide se sigue con la lista automática (el escenario "Selector configurado" lo exige). Lista por defecto (`wpasl_rendered_content_selectors`): `main`, `[role="main"]`, `article`, `#content`, `#primary`, `.site-content`, `.elementor[data-elementor-type]`; para cada selector, de las coincidencias con texto (tras la limpieza del paso 3) se toma la de mayor `strlen( textContent )`; sin coincidencias, `body`. Devolver `selector` permite que el diagnóstico diga cuál coincidió.
3. Limpieza dentro de la región, antes de medir texto: `script, style, noscript, template, nav, header, footer, aside, form, iframe, svg, button, input, select, textarea, [hidden], [aria-hidden="true"], .screen-reader-text` más los contenedores de constructores (`wpasl_rendered_remove_selectors`): `.elementor-location-header`, `.elementor-location-footer`, `[data-elementor-type="header"]`, `[data-elementor-type="footer"]`, `[data-elementor-type="popup"]`, `.et-l--header`, `.et-l--footer`. Se eliminan nodos, no se ocultan.
4. H1: el primer `h1` de la región cuyo texto normalizado (`DocumentBuilder::plain_text()`, espacios colapsados, comparación sin distinguir mayúsculas) coincida con el título se elimina; `DocumentBuilder` ya escribe `# <título>`.
5. Salida: `saveHTML()` de los hijos de la región (fragmento), que sigue el camino actual (`wpasl_markdown_html` → `LeagueConverter::convert()`, que vuelve a limpiar `script`/`form`/… y absolutiza URLs con la base del permalink). Si el fragmento no tiene texto → `ok => false`, `error => no_content`.

Traducción de selectores (`ContentExtractor::to_xpath()`, estática, pública para los tests): gramática `lista := compuesto ( ',' compuesto )*`, `compuesto := simple ( (' ' | '>') simple )*`, `simple := etiqueta? ( '#id' | '.clase' | '[attr]' | '[attr="valor"]' | "[attr='valor']" )*`. `tag` → `//tag` (`*` sin etiqueta), `#id` → `[@id='id']`, `.c` → `[contains(concat(' ', normalize-space(@class), ' '), ' c ')]`, `[a]` → `[@a]`, `[a="v"]` → `[@a='v']`, descendiente → `//`, hijo → `/`, coma → `|`. Valores con comillas simples se escapan con `concat()`. Cualquier otra sintaxis (`:pseudo`, `::`, `+`, `~`, `*=`, `^=`, `$=`) devuelve `null`, y `Settings::sanitize_key_value( 'content_selector' )` conserva el valor anterior con `add_settings_error( Settings::OPTION, 'content_selector', <mensaje con el subconjunto> )`. Sanear un valor válido es idempotente (se recortan espacios y se colapsan separadores).

Alternativa descartada: usar la `HtmlConverter` de league sobre el `body` completo confiando en `remove_nodes`. Convierte menú, pie y widgets, y no permite quitar el H1 duplicado ni elegir región; el DOM previo es barato (ya se hace en `clean()`) y da control.

### A3. Meta box: `_wpasl_content_source` junto a la exclusión

`ExcludeMetaBox` gana la constante `SOURCE_META = '_wpasl_content_source'`, un `<select>` "Markdown content source" con "Follow the settings" (`''`), "Editor content" (`editor`) y "Rendered page" (`rendered`), y su guardado en `save()` (mismo nonce; valor vacío → `delete_post_meta()`). `register_meta()` registra la clave por tipo habilitado con `type => 'string'`, `single`, `default => ''`, `show_in_rest`, `sanitize_callback` que devuelve `editor`, `rendered` o `''`, y el mismo `auth_callback`; `hide_meta_from_readers()` pasa a ocultar la lista `[ META, SOURCE_META ]`. El nombre de la clase se mantiene (renombrarla tocaría `Plugin`, tests y la spec sin ganancia); el título del meta box ya es "Agent Support Layer".

### A4. Ajustes: `content_source` por tipo y `content_selector`

`Settings::defaults()` gana `'content_source' => array()` (mapa `post_type => auto|editor|rendered`; ausente = `auto`) y `'content_selector' => ''`; ambas en `TAB_KEYS['general']`. Saneado: `content_source` recorre `selectable_post_types()`, conserva solo `editor`/`rendered` y descarta `auto` (así el almacenamiento queda vacío por defecto y un tipo nuevo hereda `auto`); `content_selector` según C1. `GeneralTab::render()` imprime, dentro de la fila "Content types", un `<select>` por tipo habilitado (visible siempre; los tipos no habilitados no lo muestran) con la descripción: "Auto: use the rendered page when the item has an assigned template, was built with a page builder, uses a fixed theme template or has an empty editor; otherwise the editor content."; y una fila "Content selector (CSS)" con `<input type="text" class="regular-text">` y descripción del subconjunto y del valor vacío. `GenerationStatus::render()` añade las filas "Items with a rendered-page failure" y "Last rendered-page failure" y el aviso `notice-warning` cuando hay fallos.

### D1. WP-CLI

`wp wpasl status` añade `render_failed` y `last_render_error` (`<motivo> (#id, <fecha ISO>)` o `none`). Nuevo `wp wpasl source <id>`: `get_post()`, elegibilidad (error con `Eligibility::reason()` cuando no es elegible), `ContentSource::resolve()` y salida `source`, `reason`, `selector` (el configurado o `auto`); `--format` como `status`. Sirve para comprobar en vivo una entrada sin regenerar nada.

### D2. Diagnóstico: objetivo `render`, informe y aviso

- `CrawlerProbe::site_targets()` añade `'render' => RenderedPage::url( $post )` tras `markdown_url` cuando hay entrada de muestra. `probe_site()` pide `render` con `Accept: text/html` y la cabecera `X-WPASL-Render: 1` (nuevo parámetro `$headers` opcional en `fetch()`), y analiza el cuerpo antes de descartarlo: `fetch()` gana un parámetro `callable|null $analyze` cuyo resultado (`array( 'content_region' => selector|'' )`, calculado con `ContentExtractor::find_region()` sobre el cuerpo recibido, hasta `MAX_RESPONSE_BYTES`) se fusiona en el resultado; el cuerpo no se guarda. `KEEP_BODY` no cambia.
- `Report::site_checks()`: clave `render`, etiqueta "Rendered page (loopback)": redirección → advertencia (mensaje existente); `status !== 200` o `error` → error con el texto "…; the site cannot fetch its own pages, items whose content source is the rendered page are served with the editor content"; `Content-Type` con `text/markdown` → error "the render marker was ignored"; sin `text/html` → advertencia de tipo (mensaje existente); 200 + HTML sin `content_region` → advertencia "no content region found, the whole body would be used; set the content selector"; en otro caso correcto "HTTP 200, text/html, content region <selector>".
- `DiagnosticsTab`: `render_render_failures_notice()` lee `Runner::status()` y muestra el aviso de la spec cuando `render_failed > 0` (independiente del informe, como el aviso de Cache Enabler); `curl_commands()` añade `curl -s -H 'X-WPASL-Render: 1' '<url>'` cuando hay muestra; el checklist gana la línea sobre loopback. `Report::normalize()` ya trata claves ausentes como no disponibles, así que un informe anterior sin `render` se renderiza sin avisos.

## Risks / Trade-offs

- [El loopback añade hasta 10 s por ítem `rendered`] → acotado por la deadline de la ejecución (B3), reintento al frente en la siguiente ejecución, y solo los ítems que las condicionales marcan; un sitio sin constructores ni plantillas fijas no hace ninguna petición.
- [Hosts que bloquean peticiones a sí mismos (WAF, `allow_url_fopen`, DNS interno, un solo worker PHP)] → fallo registrado sin descartar el ítem, documento con el editor, aviso en General y Diagnóstico con causas y `curl` para reproducir; la comprobación `render` del diagnóstico lo detecta antes de que se note en los documentos.
- [La región automática elige mal (por ejemplo `article` de un comentario o `main` con listados relacionados)] → el mayor texto entre coincidencias, la lista filtrable, el selector configurable y `wp wpasl source` para inspeccionar; `nav`/`aside`/`footer` se eliminan siempre.
- [Un documento de respaldo (`source: editor`) se sirve con `max-age` del intervalo tras un fallo bajo demanda] → aceptado: es el comportamiento actual; el ítem se repara en la siguiente ejecución. Alternativa (`no-store` para documentos de respaldo) descartada para no acoplar cabeceras al contenido.
- [`wpasl_render=1` permite a cualquiera sortear la caché de página] → cualquier cadena de consulta ya lo permite con Cache Enabler; la respuesta es el HTML normal sin efectos secundarios.
- [Detección de constructores con claves de meta erróneas o desactualizadas] → verificación por constructor en la tarea de implementación, filtro para ampliar, y las condicionales 3c/3d como red.
- [Leer archivos de plantilla en cada generación] → jerarquía corta, `locate_template()` es `file_exists()`, lectura acotada a 256 KB y caché por `ruta:mtime` por proceso; un archivo ilegible se trata como inconcluyente.
- [`State::save()` fusiona `generated` pero no otras claves] → se extiende la fusión a `render_failed`/`last_render_error` (más reciente gana) y se cubre con el escenario "Fallo de loopback bajo demanda durante una ejecución".
- [`DOMDocument::loadHTML()` con HTML5 y entidades] → mismo enfoque que `LeagueConverter::clean()` (prefijo de codificación, errores silenciados); etiquetas HTML5 desconocidas para libxml se conservan como elementos genéricos.

## Migration Plan

Sin migración de datos: las claves nuevas de ajustes y de estado tienen valores por defecto (`auto`, vacío, contadores vacíos) y `wp_parse_args()` las rellena; la meta por entrada no existe hasta que un editor la usa. Los documentos existentes se regeneran en el siguiente ciclo (o con "Regenerate everything") con la clave `source`. Rollback: desactivar el cambio deja documentos con una clave extra en el front matter, que ningún consumidor exige.

## Open Questions

- Si conviene un valor `rendered` por defecto (en vez de `auto`) para post types registrados por constructores conocidos (por ejemplo `elementor_library` no es público, así que hoy no aplica); se puede decidir con datos de uso sin cambiar specs.
- Si los documentos de respaldo deberían llevar un `X-Markdown-Source` en la respuesta; la clave del front matter ya lo expone y la cabecera se puede añadir después sin tocar la resolución.
