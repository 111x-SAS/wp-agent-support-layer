# Smoke evidence: 1.0.3 review fixes on a clean WordPress 7.1

Date: 2026-09-02. Plugin: WP Agent Support Layer 1.0.3 (distributable zip built with the same steps as
`.github/workflows/release.yml`). Environment: Docker, `php:7.4-apache` and `php:8.3-apache` with mod_rewrite,
MySQL 8.0, clean WordPress 7.1 installed by `bin/smoke-docker.sh`, default settings.

This is the evidence for tasks 2.3 and 20.4 of the OpenSpec change `fix-review-1-0-2`. Besides the checks of the
1.0.2 smoke (activation, generation, Markdown delivery, discovery files, storage protection, static front page,
batched diagnostics, real user-agent crawl check, uninstall) it exercises **finding 1 with real browser-style
requests**: after logging in with a cookie jar, the General tab is fetched (exactly two `<form>` elements: the
Settings API form and the `admin-post.php` form), "Save Changes" is posted to `options.php` with
`batch_size=10` (302 to the General tab with `settings-updated=true`, value persisted, "Settings saved." shown
once) and "Regenerate now" is posted to `admin-post.php` (302 with `wpasl_notice=scheduled`; the one-off event
is consumed at once by the spawned WP-Cron, so `last_run` changes within a second). The API catalog is now
served as `application/linkset+json` without parameters (finding 16).

Automated suites run before this smoke test on the same commit: PHPUnit 278 tests (single site, 6 skipped as
multisite-only) and 278 tests (multisite), PHPCS clean.

## "Regenerate everything" on a separate live container (PHP 8.3)

A second clean install (same image, host port 8190 mapped to the container's 8183) was kept alive for the
manual check of finding 1. The admin session was obtained through a throwaway mu-plugin with a one-time token
(no password typed anywhere), then the three actions of the General tab were exercised over HTTP:

```
logged in: 1 nonce field(s); forms: 2
before: eligible,5 generated,5 pending,0 last_run,2026-09-03T03:03:54+00:00
POST admin-post.php (Regenerate everything, full=1) -> 302 http://localhost:8190/wp-admin/tools.php?page=wp-agent-support-layer&tab=general&wpasl_notice=full
after: eligible,5 generated,0 pending,5 failed,0
General tab after the redirect shows the notice: 1
== cron events
hook	args	next_run_relative	recurrence
wpasl_generate	[]	now	1 day
wpasl_generate	["manual"]	now	Non-repeating
== run the due events with WP-CLI
Executed the cron event 'wpasl_generate' in 0.01s.
after: eligible,5 generated,5 pending,0
loopback to site_url inside the container: 000
```

"Regenerate everything" reset the cycle (generated 0, pending 5) and scheduled the one-off `manual` event. On
this container the spawned WP-Cron cannot reach `site_url()` (port 8190 only exists on the host, hence the
`000`), so the event stayed pending until `wp cron event run --due-now` executed it and regenerated the five
documents. On the smoke containers above, where the port matches, the same event runs within a second.

A hand-driven browser session was not part of this evidence: the Claude in Chrome extension was not connected,
and the requests above are the exact ones a browser sends for the three buttons.
